# 게시판 CRUD 학습 프로젝트 — 설계 문서

작성일: 2026-07-28

---

## 1. 목적과 범위

### 목적

웹 개발 학습. 게시판을 직접 만들면서 **CRUD의 전체 흐름**(브라우저 → 서버 → DB → 화면)을 이해한다.

작성자는 Python, C, C++, Java 프로그래밍 경험이 있으나 웹 개발은 처음이다. 따라서 언어 문법이 아니라 **웹의 구조**를 배우는 데 초점을 맞춘다.

### 범위

게시글 하나에 대한 CRUD 4종만 구현한다.

| 기능 | CRUD |
|---|---|
| 글 목록 보기 (10개씩 페이징) | Read |
| 글 쓰기 | Create |
| 글 상세 보기 (조회수 증가) | Read |
| 글 수정 (비밀번호 확인) | Update |
| 글 삭제 (비밀번호 확인) | Delete |

로그인이 없으므로 **작성자명 + 비밀번호** 방식으로 수정·삭제 권한을 확인한다.

### 만들지 않는 것 (YAGNI)

일부러 뺐다. 나중에 확장 과제로 붙일 수 있다.

| 항목 | 이유 |
|---|---|
| 로그인/회원가입 | 비밀번호 방식으로 권한 학습은 충분 |
| 댓글 | 1:N 관계는 CRUD를 익힌 뒤에 |
| 검색 | 페이징 완성 후 확장 과제로 적합 |
| 파일 첨부 | 파일 저장소는 결이 다른 주제 |
| 조회수 중복 방지 | 새로고침마다 오르는 게 정상 (학습용) |
| 자동화 테스트 | 지금은 흐름 이해가 우선 |
| 반응형 디자인 | 기본 CSS만 |

### 학습 목표

프로젝트 완료 시 습득하는 것:

- **HTTP** — GET/POST/PUT/DELETE의 의미, 상태 코드, 요청·응답 구조
- **REST API** — 주소와 메서드로 자원을 다루는 방식
- **CRUD** — DB의 insert / find / update / delete
- **비동기 JavaScript** — `fetch`, `async/await`
- **DOM 조작** — 데이터로 화면 그리기
- **NoSQL** — 문서형 DB, projection, `$inc`, 인덱스
- **서버리스** — 함수 단위 배포, 연결 재사용, 콜드 스타트
- **보안 기초** — 해싱, XSS, 서버 검증, 환경변수 관리
- **배포** — 인터넷에 올려서 실제로 접속되게 하기

## 2. 기술 스택

| 항목 | 선택 |
|---|---|
| 화면 | HTML + CSS + JavaScript (프레임워크 없음) |
| 통신 | `fetch`로 JSON 주고받기 |
| 서버 | Vercel Serverless Functions (Node.js) |
| DB | MongoDB Atlas (M0 무료 티어) |
| 배포 | Vercel (Hobby 무료) |
| 라이브러리 | `mongodb`, `bcryptjs` |

### 스택 선택 근거

프론트엔드와 백엔드가 **모두 JavaScript**라 언어 전환 부담이 없다. 프레임워크(React 등)를 쓰지 않으므로 브라우저가 실제로 무엇을 하는지 가려지지 않는다.

`bcrypt` 대신 `bcryptjs`를 쓰는 이유: `bcrypt`는 C++ 네이티브 컴파일이 필요해 서버리스 환경에서 문제가 생길 수 있다. `bcryptjs`는 순수 JavaScript라 어디서나 동작한다.

### 아키텍처 형태

서버는 **JSON만** 응답하고, **화면은 브라우저의 JavaScript가 만든다.**

```
① 브라우저에서 index.html 열기
        ↓
② JS가 fetch('/api/posts?page=1') 호출
        ↓
③ Vercel이 api/posts/index.js 함수를 깨움
        ↓
④ 함수가 MongoDB Atlas에 "글 10개 줘" 요청
        ↓
⑤ DB가 문서 10개 반환
        ↓
⑥ 함수가 JSON으로 응답
        ↓
⑦ JS가 그 JSON을 받아 HTML 표로 그림
```

### 파일 분리 기준

**화면 하나 = HTML 1개 + JS 1개.** "이 화면이 이상하다"가 곧 "이 파일을 고쳐야 한다"가 되도록 했다.

### Vercel의 라우팅 규칙

`api/` 폴더 안의 파일은 자동으로 API 주소가 된다.

| 파일 | 자동 생성되는 주소 |
|---|---|
| `api/posts/index.js` | `/api/posts` |
| `api/posts/[id].js` | `/api/posts/아무값` |

`[id]`처럼 대괄호를 쓰면 주소의 그 자리 값을 함수가 `req.query.id`로 꺼내 쓸 수 있다.

### DB 연결 재사용 (`lib/db.js`)

서버리스 함수는 요청이 올 때만 잠깐 깨어났다가 사라진다. 요청마다 DB에 새로 접속하면 MongoDB Atlas 무료 티어의 연결 한도(500개)를 금방 넘긴다.

그래서 연결을 **전역 변수에 담아두고 재사용**한다.

```js
// 개념 표현
let cached = null;

export async function getDb() {
  if (cached) return cached;        // 이미 연결돼 있으면 재사용
  cached = await MongoClient.connect(process.env.MONGODB_URI);
  return cached;
}
```

서버리스에서 거의 항상 필요한 패턴이다.

## 4. 데이터 모델

### MongoDB 용어 대응

| SQL | MongoDB |
|---|---|
| 데이터베이스 | 데이터베이스 |
| 테이블 | **컬렉션** (collection) |
| 행(row) | **문서** (document) |
| 열(column) | **필드** (field) |

`board` 데이터베이스 안에 `posts` 컬렉션 하나만 사용한다.

### 게시글 문서

```js
{
  _id:          ObjectId("68f2a1b3c4d5e6f7a8b9c0d1"),  // 자동 생성
  title:        "안녕하세요 첫 글입니다",
  content:      "게시판 만들기 연습 중입니다.\n잘 부탁드려요.",
  author:       "홍길동",
  passwordHash: "$2a$10$N9qo8uLOickgx2ZMRZo...",       // 해시된 비밀번호
  views:        7,
  createdAt:    ISODate("2026-07-28T05:30:00Z")
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `_id` | ObjectId | 글의 고유 번호. 넣지 않아도 MongoDB가 자동 생성 |
| `title` | String | 제목 (1~100자) |
| `content` | String | 내용 (1~5000자) |
| `author` | String | 작성자명 (1~20자) |
| `passwordHash` | String | bcrypt로 해시된 비밀번호 |
| `views` | Number | 조회수. 초기값 0 |
| `createdAt` | Date | 작성 일시 |

### `_id` 타입 변환 주의

`_id`는 문자열이 아니라 **ObjectId 타입**이다. 브라우저에서는 문자열로 오므로 DB에 쓸 때 변환해야 한다.

```js
import { ObjectId } from 'mongodb';
const _id = new ObjectId(req.query.id);   // 문자열 → ObjectId
```

이걸 빼먹으면 "분명 있는 글인데 못 찾는다"는 현상이 생긴다. 초보자가 가장 많이 겪는 실수다.

### 비밀번호 해싱

원문을 저장하지 않는다.

```
저장할 때:  "1234"  →  bcrypt.hash()  →  "$2a$10$N9qo8uL..."  → DB
확인할 때:  입력값 + DB의 해시  →  bcrypt.compare()  →  true / false
```

해시는 되돌릴 수 없다. DB를 열어봐도 원래 비밀번호를 알 수 없고, "맞는지 틀린지"만 확인할 수 있다.

학습용이라도 이렇게 하는 이유는, 평문 저장이 습관이 되면 실제 서비스에서 사고가 나기 때문이다. 코드는 두 줄 차이다.

### Projection — 필요한 것만 가져오기

목록 화면에는 본문과 비밀번호 해시가 필요 없다.

```js
.find({}, { projection: { content: 0, passwordHash: 0 } })
```

- **성능:** 본문 5000자 × 10개를 쓸데없이 실어 나르지 않는다
- **보안:** `passwordHash`는 **어떤 응답에도 포함되지 않는다**

### 인덱스

목록은 항상 최신순 정렬이므로 인덱스를 건다.

```js
db.collection('posts').createIndex({ createdAt: -1 })
```

지금은 글이 적어 체감되지 않지만, "인덱스를 왜 만드는가"를 알아두는 것이 목적이다.

## 5. API 설계

### 엔드포인트 목록

| 메서드 | 주소 | 하는 일 | CRUD |
|---|---|---|---|
| `GET` | `/api/posts?page=1` | 글 목록 (10개씩) | Read |
| `POST` | `/api/posts` | 글 작성 | Create |
| `GET` | `/api/posts/[id]` | 글 상세 | Read |
| `PUT` | `/api/posts/[id]` | 글 수정 | Update |
| `DELETE` | `/api/posts/[id]` | 글 삭제 | Delete |

주소는 2개인데 기능이 5개인 이유는, **같은 주소라도 HTTP 메서드가 다르면 다른 동작**이기 때문이다. REST의 기본 개념이다.

```js
// api/posts/[id].js — 한 파일에서 메서드로 분기
export default async function handler(req, res) {
  if (req.method === 'GET')    return 상세조회(req, res);
  if (req.method === 'PUT')    return 수정(req, res);
  if (req.method === 'DELETE') return 삭제(req, res);
  return res.status(405).json({ error: '허용되지 않는 방식입니다' });
}
```

---

### 5-1. 목록 조회 — `GET /api/posts?page=1`

**응답 (200)**
```json
{
  "posts": [
    { "_id": "68f2a1...", "title": "첫 글", "author": "홍길동",
      "views": 7, "createdAt": "2026-07-28T05:30:00Z" }
  ],
  "currentPage": 1,
  "totalPages": 5,
  "totalCount": 47
}
```

**페이징 구현**

```js
const perPage = 10;
const skip = (page - 1) * perPage;   // 3페이지 → 20개 건너뛰기

const posts = await col.find({}, { projection: { content: 0, passwordHash: 0 } })
  .sort({ createdAt: -1 })   // 최신순
  .skip(skip)                // 앞의 20개 건너뛰고
  .limit(perPage)            // 10개만
  .toArray();

const totalCount = await col.countDocuments();
const totalPages = Math.ceil(totalCount / perPage);
```

`skip` + `limit`이 페이징의 전부다. **DB에서 필요한 만큼만 꺼내오는 것**이 핵심이다.

`page`가 숫자가 아니거나 1보다 작으면 1로 처리한다.

---

### 5-2. 글 작성 — `POST /api/posts`

**요청**
```json
{ "title": "첫 글", "content": "내용입니다",
  "author": "홍길동", "password": "1234" }
```

**처리 순서**
```
검증 → 비밀번호 해시 → views: 0, createdAt: 현재시각 추가 → insertOne
```

**응답 (201 Created)**
```json
{ "_id": "68f2a1b3c4d5e6f7a8b9c0d1" }
```

`_id`를 돌려주는 이유는 브라우저가 곧바로 그 글의 상세 페이지로 이동해야 하기 때문이다.

---

### 5-3. 상세 조회 — `GET /api/posts/[id]`

**응답 (200)**
```json
{ "_id": "68f2a1...", "title": "첫 글", "content": "내용입니다",
  "author": "홍길동", "views": 8, "createdAt": "2026-07-28T05:30:00Z" }
```

`passwordHash`는 응답에서 제외된다.

**조회수 처리 — 쿼리 파라미터로 구분**

상세 페이지(`view.html`)와 수정 화면(`edit.html`)이 같은 API를 쓴다. 수정하려고 열었는데 조회수가 오르면 안 된다.

```
GET /api/posts/68f2a1...?countView=1    ← view.html (조회수 +1)
GET /api/posts/68f2a1...                ← edit.html (조회수 그대로)
```

```js
if (req.query.countView === '1') {
  post = await col.findOneAndUpdate(
    { _id },
    { $inc: { views: 1 } },
    { returnDocument: 'after', projection: { passwordHash: 0 } }
  );
} else {
  post = await col.findOne({ _id }, { projection: { passwordHash: 0 } });
}
```

`$inc`는 "지금 값이 뭐든 1을 더해라"라는 뜻이다. 값을 읽어와 +1 하고 다시 저장하면 동시에 두 명이 들어왔을 때 하나가 씹힌다. `$inc`는 DB가 원자적으로 처리해 그런 문제가 없다.

참고: 원래 `GET`은 데이터를 바꾸지 않는 것이 HTTP의 약속이지만, 조회수는 그 원칙을 어긴다. 실제 서비스도 겪는 현실적 타협이다.

> **주의 — `findOneAndUpdate`의 반환 형태는 드라이버 버전마다 다르다.**
> `mongodb` 드라이버 v4/v5는 `result.value`에 문서가 들어 있고, v6부터는 문서를 직접 반환한다.
> 구현 시 설치된 버전을 확인하고 맞춰야 한다. 안 맞으면 "데이터가 `undefined`"로 나타난다.

---

### 5-4. 글 수정 — `PUT /api/posts/[id]`

**요청**
```json
{ "title": "수정된 제목", "content": "수정된 내용", "password": "1234" }
```

**처리 순서**
```
글 찾기 → 없으면 404
   ↓
bcrypt.compare(입력 비밀번호, DB의 해시)
   ↓
틀리면 401 / 맞으면 title·content만 업데이트
```

`author`와 `createdAt`은 수정하지 않는다. 작성자가 바뀌면 안 된다.

**비밀번호 확인 시점: 저장할 때 한 번**

```
view.html에서 [수정] 클릭
   → edit.html 열림 (기존 제목·내용이 채워져 있음)
   → 고치고, 비밀번호 입력, [저장]
   → 이때 서버가 비밀번호 검증
   → 맞으면 저장 후 상세로 이동 / 틀리면 에러 메시지
```

수정 화면 진입 전에 비밀번호를 먼저 묻는 방식도 있으나, 그러려면 "비밀번호 확인 전용 API"가 하나 더 필요하다. 학습용에서는 단순한 쪽을 택했다. 남의 글을 수정창에서 볼 수 있지만, 어차피 상세 페이지에서 다 보이는 내용이다.

---

### 5-5. 글 삭제 — `DELETE /api/posts/[id]`

**요청**
```json
{ "password": "1234" }
```

수정과 동일하게 비밀번호를 확인하고, 맞으면 `deleteOne`.

**응답 (204 No Content)** — 성공했고 돌려줄 내용이 없다는 뜻.

---

### 5-6. 상태 코드 규칙

| 코드 | 언제 | 예 |
|---|---|---|
| `200` | 성공 | 목록·상세 조회, 수정 완료 |
| `201` | 만들어짐 | 글 작성 완료 |
| `204` | 성공, 내용 없음 | 삭제 완료 |
| `400` | 요청이 잘못됨 | 제목이 비었음, 100자 초과, 잘못된 id 형식 |
| `401` | 권한 없음 | 비밀번호 틀림 |
| `404` | 없음 | 이미 삭제된 글 |
| `405` | 잘못된 메서드 | `/api/posts`에 `DELETE` 전송 |
| `500` | 서버 오류 | DB 연결 실패 등 |

에러 응답 형식은 통일한다.

```json
{ "error": "비밀번호가 일치하지 않습니다" }
```

             │ 글쓰기              │ 제목 클릭

### 6-2. `write.html` — 글쓰기

```
┌──────────────────────────────────────────────┐
│  글쓰기                                       │
├──────────────────────────────────────────────┤
│  제목    [                              ]     │
│  작성자  [           ]                        │
│  비밀번호[           ]  (수정·삭제 시 필요)   │
│  내용    ┌──────────────────────────────┐    │
│          │                              │    │
│          └──────────────────────────────┘    │
│                          [ 취소 ]  [ 등록 ]   │
└──────────────────────────────────────────────┘
```

**`js/write.js`**

```
1. [등록] 클릭
2. 입력값 읽고 간단히 확인 (빈 칸 없나)
3. fetch('/api/posts', { method: 'POST', body: JSON.stringify({...}) })
4. 성공(201) → 응답의 _id로 view.html?id=... 이동
5. 실패 → 에러 메시지 표시
```

**검증은 두 곳에서 한다**

| 위치 | 목적 | 없으면 |
|---|---|---|
| 브라우저(JS) | 사용자 편의. 즉시 알려주기 | 서버 왕복해야 알 수 있어 느림 |
| **서버** | **진짜 방어** | **개발자도구로 우회 가능** |

브라우저 검증은 건너뛸 수 있다. 개발자도구를 열면 아무 데이터나 서버로 보낼 수 있다. 따라서 **서버 검증이 진짜**이고 브라우저 검증은 편의 기능이다. 이 감각이 웹 보안의 출발점이다.

### 6-3. `view.html` — 글 상세

```
┌──────────────────────────────────────────────┐
│  안녕하세요 첫 글입니다                        │
│  홍길동 · 2026-07-28 14:30 · 조회 8            │
├──────────────────────────────────────────────┤
│                                              │
│  게시판 만들기 연습 중입니다.                  │
│  잘 부탁드려요.                               │
│                                              │
├──────────────────────────────────────────────┤
│  [ 목록 ]                    [ 수정 ] [ 삭제 ] │
└──────────────────────────────────────────────┘
```

**`js/view.js`**

```
1. 주소창에서 id를 읽음
2. fetch('/api/posts/68f2a1...?countView=1')     ← 조회수 +1
3. 받은 데이터를 화면에 채움
4. [수정] → edit.html?id=68f2a1... 이동
5. [삭제] → 비밀번호 입력 영역 표시 → DELETE 요청 → 성공 시 목록으로
```

**XSS 방지 — `textContent`를 쓴다**

```js
element.innerHTML = post.content;   // ❌ 위험
element.textContent = post.content; // ✅ 안전
```

`innerHTML`을 쓰면 본문에 `<script>alert('해킹')</script>`가 들어 있을 때 **그 코드가 실제로 실행된다.** 이것이 XSS(크로스 사이트 스크립팅)다.

`textContent`는 무슨 글자가 들어와도 그냥 글자로 표시한다. 줄바꿈은 CSS `white-space: pre-wrap`으로 살린다.

**삭제 확인 방식**

`confirm()` / `prompt()` 같은 브라우저 기본 팝업 대신 화면 안에 입력 영역을 펼친다.

```
[ 삭제 ] 클릭
    ↓
┌────────────────────────────────────┐
│ 비밀번호 [        ]  [확인] [취소]  │
└────────────────────────────────────┘
```

기본 팝업은 스타일을 줄 수 없고, 자동화 도구나 테스트에서 걸림돌이 된다.

### 6-5. `js/api.js` — 공통 모듈

4개 화면이 모두 `fetch`를 쓰므로 한 곳에 모은다.

```js
export async function getPosts(page)           // 목록
export async function getPost(id, countView)   // 상세
export async function createPost(data)         // 작성
export async function updatePost(id, data)     // 수정
export async function deletePost(id, password) // 삭제
```

각 함수가 **에러도 통일해서 처리**한다. 서버가 400/401/404를 주면 응답 안의 `error` 메시지를 꺼내 예외로 던지고, 화면 쪽 JS는 그것을 받아 표시만 한다.

이렇게 나누면 **"서버와 대화하는 일"과 "화면을 그리는 일"이 분리**된다. API 주소가 바뀌어도 `api.js` 한 파일만 고치면 된다.

## 7. 검증 규칙

서버(`api/`)에서 **반드시** 확인한다. 브라우저 검증은 같은 규칙을 미리 알려주는 용도다.

| 항목 | 규칙 | 위반 시 메시지 |
|---|---|---|
| 제목 | 필수, 1~100자 | "제목을 입력해주세요" / "제목은 100자 이내로 입력해주세요" |
| 내용 | 필수, 1~5000자 | "내용을 입력해주세요" / "내용은 5000자 이내로 입력해주세요" |
| 작성자 | 필수, 1~20자 | "작성자를 입력해주세요" / "작성자는 20자 이내로 입력해주세요" |
| 비밀번호 | 필수, 4자 이상 | "비밀번호는 4자 이상이어야 합니다" |
| `id` | 유효한 ObjectId 형식 | "잘못된 요청입니다" (400) |

앞뒤 공백은 `trim()`으로 제거한 뒤 검사한다. 공백만 입력한 제목은 빈 제목이다.

### id 형식 검사가 필요한 이유

`/api/posts/hello` 같은 값이 오면 `new ObjectId("hello")`가 **예외를 던져 500 에러**가 난다. 500은 "서버가 잘못했다"는 뜻인데 실제로는 요청이 잘못된 것이므로 400이 맞다.

```js
if (!ObjectId.isValid(id)) {
  return res.status(400).json({ error: '잘못된 요청입니다' });
}
```

## 8. 에러 처리

### 서버 쪽

모든 핸들러를 `try/catch`로 감싸고, 예상 못 한 에러는 500으로 처리한다.

```js
try {
  // 실제 작업
} catch (err) {
  console.error(err);                                       // 서버 로그에 상세히
  res.status(500).json({ error: '서버 오류가 발생했습니다' }); // 사용자에겐 간단히
}
```

**에러 내용을 사용자에게 그대로 보내지 않는다.** DB 접속 문자열이나 파일 경로 같은 내부 정보가 노출될 수 있다. 상세 내용은 Vercel 대시보드 로그에서 확인한다.

### 브라우저 쪽

`api.js`가 에러를 예외로 던지고, 각 화면이 받아서 표시한다.

```js
try {
  const post = await getPost(id, true);
  화면에그리기(post);
} catch (err) {
  메시지표시(err.message);   // "존재하지 않는 글입니다"
}
```

| 상황 | 화면 표시 |
|---|---|
| 목록 로딩 중 | "불러오는 중..." |
| 글이 하나도 없음 | "등록된 글이 없습니다" |
| 없는 글 접근 | "존재하지 않는 글입니다" + [목록으로] 버튼 |
| 비밀번호 틀림 | 입력칸 아래 빨간 글씨 "비밀번호가 일치하지 않습니다" |
| 네트워크 끊김 | "네트워크 오류가 발생했습니다. 잠시 후 다시 시도해주세요" |

**요청 중에는 버튼을 비활성화**한다. [등록]을 두 번 눌러 글이 두 개 올라가는 것을 막는다.

## 9. 개발 환경

### 필요한 계정 (둘 다 무료)

| 서비스 | 용도 | 요금제 |
|---|---|---|
| MongoDB Atlas | DB | M0 무료 티어 (512MB) |
| Vercel | 배포 | Hobby 무료 |

### 설치

```bash
npm install mongodb bcryptjs
npm install -g vercel        # 로컬 실행용
```

### 모듈 시스템 설정

이 설계는 서버·브라우저 양쪽에서 `import` / `export`(ES 모듈)를 쓴다. 두 곳 모두 설정이 필요하다.

**서버 쪽** — `package.json`에 다음을 넣어야 `api/`와 `lib/`의 `import`가 동작한다.

```json
{ "type": "module" }
```

빠뜨리면 `Cannot use import statement outside a module` 에러가 난다.

**브라우저 쪽** — `api.js`를 불러오는 스크립트 태그에 `type="module"`이 필요하다.

```html
<script type="module" src="js/list.js"></script>
```

빠뜨리면 `Unexpected token 'export'` 에러가 난다.

또한 `type="module"` 스크립트는 **파일을 직접 열면(`file://`) 동작하지 않는다.** 반드시 `vercel dev`로 띄운 주소(`http://localhost:3000`)로 접속해야 한다.

### DELETE 요청의 본문

`DELETE /api/posts/[id]`는 비밀번호를 본문(body)에 담아 보낸다. `fetch`에서 `DELETE` + `body` 조합은 정상 동작하며, Vercel의 Node.js 런타임이 `Content-Type: application/json`을 보고 `req.body`로 파싱해 준다.

### 환경변수

DB 접속 정보는 **코드에 절대 쓰지 않는다.**

```bash
# .env.local  (git에 올리지 않음)
MONGODB_URI=mongodb+srv://아이디:비밀번호@cluster0.xxxxx.mongodb.net/board
```

```js
const uri = process.env.MONGODB_URI;
```

`.gitignore`에 `.env.local`과 `node_modules`를 넣는다. **접속 정보를 GitHub에 올리면 봇이 몇 분 만에 찾아낸다.** 실제로 흔한 사고다.

Vercel 배포 시에는 대시보드의 Environment Variables에 같은 값을 등록한다.

### 로컬 실행

```bash
vercel dev
# → http://localhost:3000
```

정적 파일 서빙과 서버리스 함수를 한 번에 띄워준다.

### Atlas 네트워크 설정

Vercel 서버리스 함수는 **IP가 고정되지 않는다.** Atlas의 Network Access에서 `0.0.0.0/0`(모든 IP 허용)을 열어야 한다.

대신 **DB 사용자 비밀번호를 길고 복잡하게** 설정한다. 학습용 프로젝트에서 표준적인 조합이다.

## 10. 검증 시나리오

자동화 테스트 대신 직접 확인하는 시나리오를 쓴다. **개발자도구 Network 탭을 켜놓고** 진행한다. 요청과 응답이 실제로 어떻게 오가는지 눈으로 보는 것이 이 프로젝트의 핵심 학습 지점이다.

### 정상 흐름

1. 글 작성 → 상세 페이지로 이동됨 → 내용이 맞음
2. 목록에 새 글이 맨 위에 보임
3. 상세를 새로고침 → 조회수가 1씩 오름
4. 수정 → 내용이 바뀜, 작성자·작성일은 그대로
5. 수정 화면을 열었다 닫음 → **조회수 안 오름**
6. 삭제 → 목록으로 돌아감, 그 글이 사라짐
7. 글 11개 이상 → 2페이지 버튼이 생기고, 눌러도 정상 동작

### 실패 흐름

8. 제목 없이 등록 → 400, "제목을 입력해주세요"
9. 틀린 비밀번호로 수정 → 401, 입력한 내용은 유지됨
10. 틀린 비밀번호로 삭제 → 401, 글이 안 지워짐
11. 삭제된 글의 주소로 접근 → 404, "존재하지 않는 글입니다"
12. `view.html?id=hello` → 400 (500 아님)

### 보안 확인

13. 개발자도구 Network에서 **어떤 응답에도 `passwordHash`가 없는지** 확인
14. 본문에 `<script>alert(1)</script>` 저장 → 상세에서 **글자 그대로 보임**, 팝업 안 뜸
15. `curl`로 제목 200자를 직접 서버에 전송 → **400으로 거부됨**

15번이 특히 중요하다. "브라우저 검증은 못 믿는다"를 직접 확인하는 과정이다.

## 11. 설계 결정 기록

브레인스토밍 과정에서 내린 주요 결정과 근거.

| 결정 | 대안 | 근거 |
|---|---|---|
| 핵심 CRUD만 (댓글·로그인 제외) | 댓글/로그인 포함 | 핵심 흐름을 확실히 익힌 뒤 확장하는 편이 학습 효과가 큼 |
| 작성자명 + 비밀번호 | 완전 자유 / 이름만 | "서버에서 요청을 검증한다"는 감각을 얻을 수 있고, 로그인으로 확장 가능 |
| 조회수 포함 | 기본 필드만 | "읽기 요청인데 데이터를 변경한다"는 상황으로 UPDATE를 한 번 더 연습 |
| 페이징 포함 | 전체 목록 출력 | "필요한 만큼만 DB에서 꺼내오기"가 Read의 핵심 |
| 화면마다 HTML 파일 분리 | HTML 1개 + JS 화면 전환 | SPA는 라우팅·상태 관리를 직접 구현해야 해 정작 배우려는 CRUD를 가림 |
